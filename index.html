1-1. Refresh Token 동시 갱신 시 500 오류

문제 원인

  • 프런트엔드 팀원 제보: 로그인 직후 토큰 갱신 API가 500을 반환
  • 서버 로그 확인 결과, 같은 Refresh Token으로 갱신 요청이 동시에 2건 이상 들어오고 있었음
  • 기존 갱신 순서: 토큰 조회 → 유효성 확인 → 기존 토큰 삭제 → 새 토큰 발급
    • 두 요청이 모두 "유효하다"고 읽은 뒤 같은 행을 삭제하려 함
    • 먼저 지운 요청은 성공, 뒤 요청은 이미 없는 행을 지우다 예외 → 500
    • 즉 "확인"과 "소비"가 서로 다른 문장이라 그 사이에 다른 요청이 끼어들 수 있는 구조

해결 과정

  1. 삭제 대신 "활성 토큰만 비활성화"하는 조건부 UPDATE로 변경
    • 확인과 변경이 한 문장이라, 같은 행을 바꾸려는 두 번째 요청은 DB에서 대기한 뒤 조건(isActive = true)을 다시 검사함
  2. 영향 행 수로 발급 여부 결정: 1이면 새 토큰 발급, 0이면 이미 쓴 토큰으로 보고 401 
    // RefreshTokenRepository.java
@Modifying
@Query("update RefreshToken r set r.isActive = false " +
       "where r.tokenHash = :tokenHash and r.isActive = true")
int deactivateIfActive(String tokenHash);

// AuthService.refresh()
if (refreshTokenRepository.deactivateIfActive(hashedToken) < 1) {
    throw new BusinessException(AuthErrorCode.UNAUTHORIZED);
}
  3. 배포 직후 발생한 2차 오류를 36분 만에 수정
    • 처음 붙인 @Modifying(clearAutomatically = true)가 UPDATE 직후 영속성 컨텍스트를 비움
    • 그 전에 조회해 둔 사용자 엔티티에 접근할 때 오류 발생 → 옵션을 제거 (커밋 00:43 → hotfix 01:19)

결과

  • 같은 토큰으로 동시 요청 10건: 200 응답 1건, 401 응답 9건 (PR에 첨부한 실행 결과)
  • 재사용된 토큰은 서버 오류(500)가 아니라 인증 실패(401)로 처리
  • 다음 날 401 제보는 브라우저 네트워크 탭에서 갱신 요청이 두 번 나가는 것을 확인해, 개발 모드 React StrictMode의 이중 호출이 원인임을 찾음 (서버는 의도대로 재사용을 거부한 것)

남은 과제: 단위 테스트는 mock 저장소 기반이라, 실제 DB에서의 동시 요청 검증은 수동 실행 결과에 의존합니다.

1-2. LLM 정규화 배치의 60초 timeout과 파싱 실패

문제 원인

  • 금감원 상품의 가입 대상과 우대 조건은 은행마다 줄글로 적혀 있어 규칙만으로 구조화할 수 없음 → 해당 필드만 Gemini로 구조화
  • 로컬 FSS 상품 97건 기준 배치 한 번에 5분 30초, 그중 4건이 약 60초 대기 후 timeout
  • 호출 단위 기록이 없어 어떤 상품이 오래 걸리는지 알 수 없었음 → 계측부터 추가
    • temperature = 0, 출력 토큰 상한 65,536 설정에서 일부 입력이 비정상적으로 긴 출력을 만들며 timeout까지 감
  • 추출 품질 문제도 함께 발견
    • "아래 조건 충족 시" 같은 포괄 문구를 실제 우대 조건으로 추출
    • 구간별로 다른 우대금리를 하나로 합쳐 버림

해결 과정

  1. 호출 단위 로깅 추가: 상품 ID, 소요시간(durationMs), 성공·실패와 예외 종류를 호출마다 기록
  2. 설정 조합을 바꿔 같은 97건으로 반복 측정 (temperature와 출력 상한을 함께 바꿨으므로 한 설정만의 효과로 보지 않음)
    설정job 시간실패실패 양상
    기존 (temp 0, 상한 65,536)5분 30초4/97약 60초 뒤 timeout
    temp 0.1, 상한 2,0483분 28초6/978.5~9.8초 내 파싱 실패
    temp 0.2, 상한 2,0482분 45초3/977.5~8.1초 내 파싱 실패
    temp 0.3, 상한 2,048 (선택, 3회)2분 52초~3분 23초4~5/977.2~8.9초 내 파싱 실패
    • 0.1~0.3 사이에 뚜렷한 우열은 없었고, 정상 출력 규모를 근거로 상한 2,048을 정함
  3. 남은 파싱 실패는 프롬프트로 해결: 7차례 반복 수정
    • 포괄 조건과 실제 우대 조건을 분리
    • %p가 명시되지 않은 조건, 총합 안내 문구는 제외
    • 구간별 차등 우대금리는 구간마다 별도 조건으로 추출
  4. LLM이 실패해도 배치는 끝나도록 실패 격리
    • 실패하면 규칙 기반 정규화 결과(draft)를 그대로 저장하고 다음 상품으로 진행
    • 실패 기록을 캐시에 남겨 6시간 동안 같은 상품 재호출을 차단, 프롬프트가 같으면 성공 캐시 재사용
    • 코드펜스(```json)로 감싼 응답도 JSON 본문만 꺼내 파싱
    // LlmEnrichmentCache.java
public boolean isFailedRetryBlocked(Instant now, Duration cooldown) {
    if (status != FAILED || lastFailedAt == null) return false;
    return lastFailedAt.plus(cooldown).isAfter(now);   // 6시간 이내면 호출 생략
}

결과

  • 97건 배치 시간 5분 30초 → 2분 52초~3분 23초 (약 38~48% 단축)
  • 약 60초짜리 timeout은 이후 6회 실행에서 0회, 실패해도 10초 안에 끝나도록 바뀜
  • 프롬프트 개선 후 같은 97건에서 파싱 실패 0건, 구간별 우대금리가 각각의 금리로 분리되는 것 확인
  • 은행 328건과 정부 63건, 총 391건을 같은 구조로 정규화해 서비스에 사용

남은 과제: 97건은 프롬프트 조정에 쓴 데이터라, 처음 보는 상품에 대한 추출 정확도는 따로 검증해야 합니다. (근거: PR #40)

2-1. 회원 탈퇴 시 계정 삭제에 30초

문제 원인

  • 탈퇴 정책은 Hard Delete: 카드 거래·매출 같은 민감정보를 남기지 않기 위해 DELETE FROM app_user 한 문장으로 지우고 나머지는 ON DELETE CASCADE에 맡김
  • PostgreSQL은 지워지는 부모 행마다 자식 테이블을 FK 컬럼으로 찾음. 그런데 자식 쪽 FK 인덱스는 자동으로 만들어지지 않음
  • 삭제 경로를 따라가 보니 4개 FK에 쓸 수 있는 인덱스가 없어 단계마다 자식 테이블 전체를 읽고 있었음
    • question_queue.judgment_id, answered_fact_id: 인덱스 없음
    • limit_bucket_entry.judgment_id: UNIQUE(user_id, tax_year, bucket_code, judgment_id)의 네 번째 컬럼이라 이 조회에 못 씀
    • judgment_override.transaction_id: WHERE active 부분 인덱스만 있어 비활성 행까지 찾는 조회에 못 씀
  • 측정(로컬 PostgreSQL 16, 사용자 100명 × 거래·판정 3,000건, 판정 30만 행): 사용자 1명 삭제에 30초, 그중 limit_bucket_entry FK 18.4초, question_queue FK 9.0초

해결 과정

  1. Flyway 마이그레이션(V9)으로 단일 B-tree 인덱스 4개 추가 
    CREATE INDEX idx_question_queue_judgment        ON question_queue (judgment_id);
CREATE INDEX idx_question_queue_answered_fact   ON question_queue (answered_fact_id);
CREATE INDEX idx_limit_bucket_entry_judgment    ON limit_bucket_entry (judgment_id);
CREATE INDEX idx_judgment_override_transaction  ON judgment_override (transaction_id);
  2. 인덱스가 늘리는 쓰기 비용을 같이 측정 (3회 중앙값)
    작업추가 전추가 후
    question_queue 6만 행 INSERT0.69초1.29초
    limit_bucket_entry 10만 행 INSERT2.63초3.96초
    질문 3만 건 답변 UPDATE0.26초0.58초
    • 행당 5~13µs, 판정 3,000건 한 번에 약 20ms 증가 → 탈퇴 한 번에 30초보다 낫다고 판단
  3. 모든 FK에 걸지는 않음: judgment_run.context_id도 인덱스가 없지만 run은 배치당 몇 건뿐이라 전체를 읽어도 싸서 제외
  4. 배포 호환성 확인: 인덱스만 추가하므로, 이전 버전으로 롤백해도 기존 코드가 깨지지 않음

결과

  • 계정 1건 DELETE 30.0~32.9초 → 0.77~1.2초
  • 커밋 시점 참조 FK 검사 0.44~0.50초 → 0.06~0.34초
  • 단위 테스트 193건, 통합 테스트 44건 통과 후 PR #117 병합

한계: 개인 PC의 PostgreSQL 16에서 2회 측정했고 실행마다 최대 1.7배 흔들려 크기 비교로만 봅니다. 운영 RDS에서는 재지 않았습니다.

2-2. 배포 단계의 빌드 실패와 배포 중 서비스 끊김

문제 원인

  • PR 검증은 통과했는데 release 배포에서 웹 이미지 빌드 실패 (10/05)
    • 웹 Dockerfile이 저장소 루트의 rules/categories.yaml을 복사하지 않았음
    • CI 러너에는 저장소 전체가 있어 npm build는 통과 → PR이 검증한 환경과 운영 이미지가 달랐던 것
  • 배포할 때마다 서비스가 끊김
    • 웹 이미지 태그가 커밋마다 바뀌어, 화면이 바뀌지 않은 배포에서도 Caddy가 재시작됨
    • 백엔드와 AI 컨테이너도 한 쌍뿐이라 교체되는 동안 API가 응답하지 못함
    • 재현 환경 측정: 배포 1회에 화면 18.1초, API 20.6초 끊김
    • 판정 작업(run)이 도는 중 배포하면 작업이 끝날 때까지 API가 63.1초 멈춤

해결 과정

  1. PR 단계에서 운영과 같은 Dockerfile로 이미지 빌드: backend, ai, web 각 job에 docker build -f deploy/*.Dockerfile 추가
  2. Caddy와 화면 파일 분리: Caddy 이미지 버전을 고정하고 화면 파일은 볼륨에 반영 → 설정 변경은 재시작 없이 caddy reload
  3. 백엔드와 AI를 blue·green 두 쌍으로 무중단 배포
    1. 쉬는 색의 backend·ai를 새 이미지로 띄우고 healthy까지 대기
    2. Caddy가 읽는 upstream.caddy를 새 색으로 교체
    3. caddy reload로 새 요청만 새 색으로
    4. 옛 쌍은 처리 중인 요청을 마친 뒤 stop
    • backend와 ai는 서로를 호출하므로 쌍으로 묶어 전환 중 새 backend와 옛 ai가 섞이지 않게 함
    • 헬스체크 기반 자동 전환 대신 reload를 택함: 옛 서버가 하던 요청은 마저 끝내고, 새 요청만 새 설정을 따르기 때문
  4. 배포 스크립트 안전장치
    • flock으로 동시 배포 차단, release 최신 SHA가 아닌 이전 배포 요청은 거부, --rollback 모드
    • Flyway 밖의 SQL은 psql -1로 한 트랜잭션에 묶어 일부만 적용되는 상황 방지
    • reload가 실패하면 upstream.caddy를 원래 값으로 복원 (팀원 리뷰 반영)
    • SSM이 실행하는 스크립트는 직전 배포의 파일이라 변경이 한 배포 늦게 반영되던 문제 → checkout 뒤 대상 커밋의 deploy.sh로 다시 실행
  5. 운영 서버를 건드리지 않고 검증: docker-in-docker로 가짜 EC2를 만들어 deploy.sh를 그대로 실행하고, 0.2초마다 화면과 API를 호출해 끊긴 시간을 측정

결과

  • 운영 이미지 빌드 누락을 PR 단계에서 잡도록 바꾸고, 같은 날 재배포 성공
  • 배포 중 끊김 화면 18.1초 → 0초, API 20.6초 → 0초 (blue·green 전환 4회 모두 0초)
